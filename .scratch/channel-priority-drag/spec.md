# 渠道拖动调整优先级

Status: ready-for-agent

## Problem Statement

管理员目前需要直接编辑渠道优先级数值来调整调用先后，难以通过列表直观完成顺序调整。用户希望在具体渠道 ID 左侧按住拖动柄上下移动，松手后完成优先级调整，列表从上到下的顺序直接表示从高到低的渠道优先级。

现有列表支持分页、搜索、筛选、标签聚合及不同字段排序。直接在任意视图中修改当前页优先级，会造成隐藏渠道、其他页面渠道与显示顺序不一致。多个管理员同时调整时，也可能覆盖彼此的结果。

## Solution

在渠道管理表格中，为具体渠道 ID 左侧增加可访问的拖动柄。仅在无搜索、无筛选、关闭标签聚合且按渠道优先级降序排列的视图中启用，其他视图提示如何切回可拖动状态。

首版支持当前页内移动。一次有效移动后，立即显示新顺序并自动保存；保存时根据全部渠道的全局顺序，将优先级统一设置为 N、N−1、……、1，其中 N 是当前渠道总数。当前页之外的渠道保持相对顺序，但优先级数值也参与重新编号。分页只影响展示，不定义独立的排序范围。

保存期间禁止再次拖动；普通保存失败恢复原顺序并提示错误。若排序基线已被其他操作改变，则拒绝覆盖，加载最新顺序并提示重新拖动。后端整体保存渠道及路由使用的优先级数据，避免出现部分渠道已更新、部分未更新的状态。

## User Stories

1. 作为渠道管理员，我希望在具体渠道 ID 左侧看到拖动柄，以便明确识别调整顺序的入口。
2. 作为渠道管理员，我希望按住拖动柄上下移动渠道，以便通过位置表达调用先后。
3. 作为渠道管理员，我希望松手后自动保存，以便不用额外点击提交按钮。
4. 作为渠道管理员，我希望松手后立即看到新顺序，以便及时确认自己的操作结果。
5. 作为渠道管理员，我希望拖动后的渠道优先级从上到下严格递减，以便显示顺序与优先选用顺序一致。
6. 作为渠道管理员，我希望每次保存都按全部渠道重新生成 N 到 1 的优先级，以便不必手工维护数值间隔。
7. 作为渠道管理员，我希望排序规则覆盖全部渠道，以便不同页面不会各自形成相互重叠的优先级。
8. 作为渠道管理员，我希望当前页拖动只改变选中渠道在该页内的位置，并保留其他渠道的相对顺序，以便调整范围可预测。
9. 作为渠道管理员，我希望翻页或刷新后仍看到已保存的顺序，以便确认调整已经持久化。
10. 作为渠道管理员，我希望仅在无搜索、无筛选、关闭标签聚合且按优先级降序显示时拖动，以便被隐藏或重新排列的渠道不会误导操作。
11. 作为渠道管理员，我希望在不满足拖动条件时看到原因及切回完整优先级视图的提示，以便知道如何继续。
12. 作为渠道管理员，我希望标签聚合行不被当作具体渠道拖动，以便不会无意移动整组渠道。
13. 作为渠道管理员，我希望首版保留现有优先级编辑功能用于跨页调整，以便仍能把后面页面的渠道提升到前面。
14. 作为渠道管理员，我希望保存期间暂时不能再次拖动，以便不会同时提交多个相互冲突的排序请求。
15. 作为渠道管理员，我希望普通保存失败时恢复拖动前的顺序并显示错误，以便不会把未保存的状态误认为已生效。
16. 作为渠道管理员，我希望其他管理员先调整优先级时，本次保存被拒绝并加载最新顺序，以便不覆盖别人的修改。
17. 作为渠道管理员，我希望单渠道编辑和标签批量编辑造成的优先级变化也能被冲突检测识别，以便其他入口不会绕过保护。
18. 作为渠道管理员，我希望读取列表后发生的渠道新增或删除不会造成静默覆盖、遗漏或误编号，以便全局排序始终针对完整且一致的集合。
19. 作为渠道管理员，我希望拖回原位置或取消拖动时不保存，以便不会仅因一次无效拖动就拆开原有同级关系。
20. 作为渠道管理员，我希望在原本有同级渠道时仍获得稳定的列表顺序，以便翻页和拖动不会因同级排序不确定而跳动。
21. 作为渠道管理员，我希望一次排序整体成功或整体失败，以便不会产生一半渠道已调整的结果。
22. 作为渠道管理员，我希望保存成功后实际请求选路采用新的渠道优先级，以便管理页面与网关行为一致。
23. 作为渠道管理员，我希望只修改顺序和渠道优先级，以便渠道权重、模型、分组及连接配置等其他设置不被改写。
24. 作为使用键盘的管理员，我希望能够聚焦拖动柄并完成同等的页内移动，以便不依赖鼠标也能管理顺序。
25. 作为使用辅助技术的管理员，我希望拖动入口、禁用原因和保存反馈具有可访问名称或通知，以便理解操作状态。
26. 作为使用不同界面语言的管理员，我希望相关提示和错误采用当前界面语言，以便准确理解排序影响。
27. 作为系统管理员，我希望重排操作遵循现有渠道写权限并由服务端校验，以便没有相应权限的访问者不能修改全局顺序。
28. 作为渠道管理员，我希望空列表或仅有一个渠道时不会出现无意义的重排提交，以便界面只提供有效操作。
29. 作为渠道管理员，我希望明确知道全局重新编号会拆开原有同级渠道，以便理解同级分流将转为优先选用和失败降级。

## Implementation Decisions

1. **领域语义**：渠道优先级数值越大，越优先参与满足请求条件的选路；渠道权重用于同级候选之间的分流。拖动改变真实渠道优先级，不增加独立的展示序号。全局重排会拆开原有同级关系；不修改渠道权重数值，也不修改现有路由重试算法。
2. **全局范围**：一次有效重排覆盖全部渠道，包括其他页面及当前未启用的渠道。分页只限制可拖动目标。若管理员无法合法读取或修改完整范围，应禁用并拒绝全局重排，不得悄悄将部分可见渠道当作全局集合。
3. **统一编号**：保存后全局渠道数为 N，优先级严格为 N 到 1。当前页内部应用本次移动，页外渠道维持相对顺序。每次有效重排都重新计算全局数值。
4. **稳定顺序**：优先级相同时必须增加确定的次级顺序，并在列表查询、分页、排序快照和保存校验中一致使用。实现默认采用渠道 ID 降序作为同级的次级顺序。该默认值用于消除现有同级列表的不确定性，不表示用户新增了同级分流偏好。
5. **表格交互**：在现有渠道表格中放置 ID 左侧拖动柄，不引入独立排序面板。优先复用现有拖动、键盘移动和按钮能力。现有可排序列表组件不是渠道表格行的直接替代品；实现前须确认其对表格行语义的支持，优先兼容扩展或组合。若仍需新增公共能力，须说明现有组件的具体能力缺口。
6. **启用规则**：仅无搜索、无筛选、关闭标签聚合且按优先级降序排列时启用。默认视图隐含的优先级降序也满足条件。其他排序方向、字段及任何缩小候选集合的视图都不允许拖动；提示应说明如何切回。标签聚合行不可拖动。
7. **操作生命周期**：只有落点有效且相对位置确实变化时才提交。取消、落在无效区域或回到原位置都不提交，也不触发全局重新编号。键盘移动遵循相同的保存、失败与冲突规则。
8. **保存反馈**：松手后乐观展示新顺序，保存期间禁止产生重叠的重排请求。禁止同一客户端尚未完成的优先级字段编辑与重排请求无序交错；复用现有字段更新调度，保证提交基线明确。
9. **错误反馈**：普通失败恢复已知的拖动前状态并提示错误。请求结果不确定时，通过重新读取服务器状态消除歧义，不自动重放整次写入。并发冲突不以旧快照回退覆盖最新状态，而是加载最新列表，提示重新拖动。
10. **新增排序契约**：渠道列表读取流程提供与全局渠道集合及其优先级对应的排序版本或等效快照标识；保存携带期望版本以及足以表达页内移动的渠道标识。服务端计算并校验完整顺序，不信任客户端提交的 N 或任意优先级数值。具体 URL、版本字段命名、快照表示及请求形状由实现选择，不将其误写为现有接口能力。
11. **冲突保护**：排序版本不匹配返回 HTTP 409，前端重新读取，不自动覆盖重试。检测范围覆盖其他重排、单渠道优先级编辑、标签批量优先级编辑，以及新增或删除导致的集合变化；与排序无关的字段变化不应无故使排序失效。
12. **原子检查与写入**：版本比较、完整集合校验和优先级更新必须构成同一并发一致性边界。所有可能改变渠道优先级或集合的既有写入路径必须参与等效的协调规则，不能只给新重排接口增加提交前比较而留下比较后被覆盖的窗口。实现须同时考虑多进程部署；进程内互斥不是完整的并发保护。
13. **整体保存**：在数据库事务中整体修改渠道优先级及路由能力中的对应优先级；不通过多次独立单渠道更新请求模拟排序。提交失败时所有变更回滚，不暴露中间状态。只更新必要字段，保留其他渠道配置。
14. **路由与缓存**：持久化成功后按既有架构同步或使相关缓存失效，确保后续请求采用已提交的新优先级。能力修复、后台缓存重建等路径不能把旧优先级重新覆盖回来，也不能因排序产生临时缺失的路由能力。缓存失败不能伪装成数据库已回滚，应通过明确反馈和状态核对恢复一致性。
15. **权限边界**：复用现有渠道优先级编辑对应的渠道写权限；既有读取和写入权限边界仍由服务端执行。本规格不重新设计认证、会话或权限模型。
16. **数据库策略**：行为必须支持 SQLite、MySQL 和 PostgreSQL。优先复用既有 ORM、事务和锁约定；SQLite 不能依赖被忽略的行锁语义。是否新增持久化排序版本尚未指定；若实现需要模型或迁移，应遵守三引擎及重复启动、升级兼容验证要求。
17. **本地化与可访问性**：复用项目翻译和可访问组件约定，为新增界面文案提供全部受支持语言。拖动柄须有明确名称，键盘可执行等效重排，操作不能破坏表格结构、现有行内编辑和行选择。

## Testing Decisions

1. **测试原则**：测试管理员可观察的交互、API 契约、数据原子性及真实选路结果；不以私有辅助函数、字段清单、实现常量或文件布局替代行为验证。采用确定输入与精确输出，避免重复覆盖同一行为。
2. **主要后端测试入口**：优先通过真实渠道控制器/API 请求进入功能，使用真实数据库观察渠道、能力数据、读取结果及冲突响应；复用已有 Gin 请求和数据库隔离设施。无需为算法、事务内部每一步分别创造新测试入口。
3. **后端测试先例**：已有渠道控制器测试提供数据库初始化及请求验证模式，模型管理数据库矩阵测试提供三引擎隔离与版本记录模式，现有配置版本冲突接口提供 HTTP 409 的契约先例；已有条件更新测试可参考并发赢家与失败方的断言方式。它们是可复用先例，不代表渠道全局排序已有实现或测试。
4. **全局重排案例**：以至少两页渠道作为输入，包含相同优先级、不同权重和停用渠道。移动当前页的一条渠道后，精确验证全局顺序、N 到 1 编号、页外相对顺序、其他配置不变，以及刷新/翻页后结果一致。例如初始全局 A、B、C、D、E、F，每页三个，将第二页 F 移到 D 前，保存后应为 A、B、C、F、D、E，优先级依次为 6、5、4、3、2、1。
5. **无效和空操作**：验证取消或原位移动不会请求保存、不会全局重新编号；空列表、单行列表、重复/不存在的渠道标识及与快照不一致的请求得到正确处理。
6. **事务一致性**：通过可控的数据库失败或既有错误注入能力触发中途失败，验证渠道和能力数据均未部分提交，已有路由能力不丢失。不要仅断言错误已返回。
7. **并发冲突**：两个客户端读取相同基线后，第一方保存成功，第二方返回 409 且不覆盖。分别覆盖单渠道编辑、标签批量优先级编辑、新增和删除造成的冲突；用受控并发验证检查与提交之间也不会丢失更新，避免通过 sleep 猜测时序。无关字段更新不应被旧排序写入覆盖。
8. **选路与缓存**：在已有渠道选路入口验证，保存前后的候选优先级与实际选用结果一致，启用缓存时也不继续使用旧顺序；设置明确的模型、分组、状态及权重，避免依赖随机结果来断言。
9. **权限回归**：复用现有渠道路由权限测试结构，验证新增保存入口遵守渠道写权限，非法调用不能写入；不扩大到本特性之外的认证重构。
10. **主要前端测试入口**：渲染真实渠道表格并模拟 API 边界，复用现有渠道表格刷新测试的查询客户端、内存路由及渠道上下文设施。验证当前页移动的用户操作、请求参数、保存期禁拖、成功刷新、普通失败回退、409 加载最新以及不自动重试。
11. **前端先例与输入方式**：复用现有自动分组顺序编辑器的拖动柄键盘重排测试模式。组件测试使用稳定的用户交互完成重排；真实指针拖动、落点、滚动、焦点和表格布局需通过已有浏览器验证设施或明确的人工检查验证，不为单次特性引入全新端到端框架。
12. **视图和可访问性**：以表格交互测试覆盖搜索、筛选、标签聚合、其他排序字段和升序下的禁用行为及原因提示；验证 ID 左侧入口的名称、键盘操作与边界位置，并确认行选择和字段编辑仍可使用。
13. **三数据库验收**：数据库相关实现必须在真实 SQLite、MySQL、PostgreSQL 实例执行；记录确切版本、命令和结果。已有测试设施支持 MySQL/PostgreSQL 测试 DSN，但未配置时的跳过不能视为矩阵通过。版本相关行为需覆盖项目支持的最低版本边界；有迁移时增加新建及代表性最新发布版本升级、重复启动和数据保留检查。
14. **检查范围**：按项目要求运行相关 Go 测试、前端类型/静态检查、翻译同步与校验及构建。优先扩展现有适合的测试文件；聚焦 Go 改动最多新增一个测试文件。不得声称只凭构建、模拟或单方言测试已完成数据库兼容验收。
15. **测试边界状态**：以上为依据已确认需求及现有测试先例拟定的执行方案。本轮用户明确要求不再采访，因此直接随规格发布，未将测试方案描述为另行获得过用户逐项确认，也未执行功能测试。

## Out of Scope

- 跨页拖动、拖动时自动翻页，以及独立的全局排序面板。
- 在搜索、筛选、标签聚合或其他排序视图内拖动。
- 只维护某页、某标签、某分组的独立顺序。
- 保留同级优先级、通过拖动加入同级分流组，或用稀疏优先级替代 N 到 1 的编号。
- 修改渠道权重、候选匹配条件、重试算法、计费或上游请求内容。
- 批量多选拖动、手动保存模式、历史版本管理或新增撤销功能。
- 删除现有优先级数值编辑能力，或要求所有既有编辑入口永久维持连续编号。
- 新建通用拖动框架、测试平台，或重构与排序无关的渠道配置与认证流程。
- 本轮实现功能、提交代码、发布 GitHub issue/PR 或部署。

## Further Notes

- 用户原始需求：

  > 针对于渠道，我想要在前端实现拖动一个具体的渠道实现优先级改变，优先级由上到下逐级递减。可以设置为具体渠道ID的左侧，按着拖动按钮之后，上下拖动，松手之后完成优先级的调整。

- 用户已确认全部七项产品决定：严格递减；乐观保存及失败回退；并发冲突拒绝覆盖；全局重排；仅完整优先级视图启用；首版仅页内移动；每次统一编号 N 到 1。已明确告知全局重排会拆开原有同级关系，并改变同级分流行为。
- 现有渠道列表默认按优先级降序且支持分页。已有单渠道及按标签更新优先级的入口，没有直接满足本规格的任意渠道全局原子重排及冲突保护契约。
- N 到 1 是每次有效拖动保存完成时的结果。现有手动优先级编辑仍可产生间隔或同级值；下一次有效拖动再统一编号。既有渠道不会仅因打开页面或升级程序而自动重排。
- HTTP 409 冲突反馈、稳定的同级次序、集合变化检测和数据库一致性是基于已确认行为形成的实现约束；具体接口名称和存储技术尚未选择。
